Prototype Operator Sheet

Airflow-First Prototype Cheat Sheet

Use this page when you want to understand what to run, what not to run, and when native Windows is good enough versus when you should switch to a container or WSL2.

What Failed On Windows

The real Airflow scheduler and webserver startup path failed on native Windows because Airflow's daemon path imports the POSIX-only pwd module. That means the browser-observable Airflow UI path is not the right prototype path on this machine.

Implication: native Windows is fine for smoke tests and in-process dag.test() style validation, but not for reliable scheduler/webserver observation.

Use This On Native Windows

  1. Run the smoke tests.
  2. Use the domain observation database as your evidence source.
  3. Treat this as logic validation, not live scheduler validation.
d:/fec-data/.venv/Scripts/python.exe -m unittest tests.test_airflow_first_smoke -v

This verifies schema bootstrap, change detection, snapshot updates, compact failure diagnostics, DAG defaults, and manual override validation.

Do Not Expect This To Work Natively

airflow scheduler
airflow webserver --port 8080

These commands are the right shape for Linux, WSL2, or a container, but they are not the correct expectation for native Windows in this prototype.

Fastest Native Windows Validation Loop

  1. Run the smoke test suite.
  2. Inspect db/fec-observations.sqlite if you want proof rows.
  3. Use the optional SQL checks from the runbook.
duckdb -c "ATTACH 'db/fec-observations.sqlite' AS obs (TYPE SQLITE); SELECT observed_at, cycle, table_name, fetch_status, change_detected, dag_run_id, map_index, try_number FROM obs.airflow_upstream_observation_history ORDER BY observation_id DESC LIMIT 20;"

Containerization Advice

Recommendation: yes, containerize if you want to observe the real Airflow UI and scheduler behavior.

Containerization is justified here because the failure mode is platform-related, not an app logic bug. Your prototype already proved that:

  • The DAG and persistence logic parse and run inside Python.
  • The full Airflow daemon path breaks because native Windows is not a supported target for this workflow.
  • The web UI is part of what you want to evaluate, so you need a runtime that can actually host it.

When To Containerize

  • Containerize now if your next question is, "What does the DAG look like in the Airflow UI?"
  • Do not containerize yet if your next question is only, "Does the observation logic work?"

Best Next Runtime Options

Option A: WSL2

Best if you want a lighter-weight Linux runtime on the same machine.

  • Good for real Airflow scheduler and webserver.
  • Closer to normal local developer workflow.
  • Lower setup overhead than full container orchestration.

Option B: Docker Compose

Best if you want a reproducible prototype environment you can restart cleanly.

  • Good if this prototype may be shared or repeated.
  • Makes runtime dependencies explicit.
  • Separates Airflow dependencies from your current dbt-oriented venv.

My Advice

If your immediate goal is observation, not more code, use a container or WSL2 next. The reason is simple: the main missing capability is the live Airflow UI, and native Windows is exactly where that path is breaking.

If you want the lowest-friction prototype move, I would choose WSL2 first. If you want the cleanest long-lived evaluation environment, I would choose Docker Compose.
